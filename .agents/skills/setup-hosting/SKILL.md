name: setup-hosting
description: Choose a host, record its fit and prepare an approved empty Place; checking is /check-live.
---

Read `hosting/handover.json` and the organisation's local `hosting/place-record.json`
if one exists. Use the sibling `host-fit/SKILL.md` and its script for questions,
fit reports, suggestions and recording. Locate the sibling beside this skill
in the installed kit, including when loaded through a plugin. Use its command
prefix for that install route from the project root; never use `cd`. Ask at
most the three returned questions in plain words. Keep temporary answers at
the path and with the cleanup described in host-fit. Explain the not-sure
response as the script directs.
Do not ask about residency or ask about long work when the handover supplies
its duration.

Show every fit line and the suggestion with its trade-off and proof status.
The proven menu is empty today. Let the person choose, including keeping an
existing place. Follow host-fit's warn-once rule for a shortfall and record
accepted shortfalls with the person's words and date. Write only the local
place record using `record`; preserve existing infrastructure fields. When
there is no private place repository yet, save the choice-only
`hosting/place-record.json` beside the handover as a draft for that repository.
Tell the person where it is. This records a preference, not approval to create infrastructure.
Do not create a repository or change the handover. A saved choice alone does not authorise a provider call.

After recording, explain that no infrastructure exists yet. For a chosen Coolify
on Hetzner place, the experimental empty-Place path has offline checks but no
real-run proof. Keep it off the proven menu. If the person wants to create that
place, follow the sibling host-fit recipe's `setup.md` and `scripts/setup.py`
from the private place repository. Use the installed sibling paths, including
in plugins. Prepare the root and non-secret settings for review. Obtain
permission for provider reads, show the saved-plan summary and let the person
run approval themselves. Never answer a hidden prompt or manufacture approval.

Continue only through the approved saved apply, bootstrap reads, the person's
first-admin claim, localhost destination discovery and each named MCP effect.
Each write has its own approval. Keep the internal firewall lane closed until
the claim is read back. Use `lane.py` for a separately approved public-lane
test. The final record stage preserves the unchanged choice and writes the
created empty place to `hosting/place-record.json`. On failure, stop and report
what may exist and the retirement route from the recipe. Never retry an
uncertain write. No provider calls are permitted in an offline rehearsal.

Other creation and adoption routes remain unbuilt. Backups, alerts and putting
a tool live are outside this empty-Place flow. Do not claim them. Checking a
place belongs to `/check-live`.
